# Walkthrough

Every file in the repo: what it does, why it exists, and the design decision behind it, in plain English. It is written for someone who reads code but doesn't live-code.

Read [SPEC.md](SPEC.md) first if you want the rules; this file is about where each rule lives.

## The shape of the repo

| Folder | What it is |
| --- | --- |
| `docs/` | The spec, the rule register, the design notes, and this file |
| `mock_api/` | A local reference mock of the authorization API |
| `spend_guard/` | The integration side: client, payment gate, ledger, verifier, webhook receiver, reconciliation |
| `mcp_server/` | An MCP server that offers the gate to a model as two tools |
| `integrations/openai_agents/` | The same gate as an OpenAI Agents SDK tool, with a guardrail |
| `evals/` | Scripted agent policies run through ten scenarios, and the report |
| `demo/` | `make demo`: the whole story in a terminal |
| `scripts/` | Checks that keep the docs and tests honest, and a seeding helper |
| `tests/` | The test suite. No network, no API keys, no waiting on real time |

One idea runs through all of it: **a limit written in a prompt is a request. The check has to live in the code that holds the payment credentials.** The mock answers "may this agent spend this?" and signs the answer. `PaymentGate` is the code that holds the credentials and acts on the answer.

## Docs and scripts

### `docs/SPEC.md`

**What it does:** The reference spec. It covers the endpoints, the decision object, the 8 decision codes and their evaluation order, mandates, reviews, idempotency, errors, rate limits, the verdict token, the order of checks when verifying one, webhooks, and what the integration must do.

**Why:** Both halves of the repo are built against one written set of rules, instead of each piece of code relying on memory.

### `docs/RULES.md` and `scripts/check_rules.py`

**What they do:**
- `RULES.md` is the rule register: one numbered row per behaviour the code implements. Each row links to the spec section that states the rule, names the function that implements it, and names the test that proves it.
- `check_rules.py` fails if:
  - a row's spec link points at a heading that doesn't exist
  - a row has no implementation or no test
  - a cited function or test doesn't exist
  - a test's docstring doesn't name its rule id

**Why:** It makes "this is tested" checkable instead of a claim. You can go from a test, to the rule, to the sentence in the spec, and back.

**Design decisions:**
- **Rows marked "Design decision"** are places with a real choice, where the repo took the stricter option. The bigger ones are explained in `DESIGN_NOTES.md`.
- **The checker needs only the repo,** so it runs in CI.

**Run it:** `make rules` or `uv run python scripts/check_rules.py`

### `scripts/check_readme.py`

**What it does:** Fails if the README's eval table differs from `EVALS.md`, or if its test count or rule count differs from the repo.

**Why:** Numbers in a README go stale without anyone noticing. This runs in CI, so they can't.

**Run it:** `make readme`

### `scripts/mutation_check.py`

**What it does:** Copies the repo to a temporary folder, breaks one safety-critical line (12 of them, one at a time), runs the test that should notice, and expects that test to fail. The working tree is never touched. The tests run with `python -B` (no cached bytecode), because a broken line of the same length written in the same second would otherwise run the original's cached bytecode and look like it passed.

**Why:** A test that still passes when the code is wrong proves nothing. This is how you find that out. It found one real gap while this repo was being built: nothing tested the ledger's atomic claim on the one path where it is the only guard. That test now exists.

**Run it:** `make mutation`

### `docs/DESIGN_NOTES.md`

**What it does:** Explains the trade-offs behind the less obvious rules (verdict-first allowlisting, `order_id:attempt` keys, the velocity backoff, `already_paid` on a lost race, expiry-day handling and others), what each one costs, and which questions are still open.

### `docs/MCP.md`

**What it does:** How to run the MCP server locally and connect it to Claude Desktop or Claude Code, with config snippets and things to try.

### `README.md`, `EVALS.md`, `LICENSE`

- `README.md` is the front page: the problem, a diagram, the quickstart, the eval table, and what the repo does not do.
- `EVALS.md` is generated by `make evals`. Don't edit it by hand.
- `LICENSE` is MIT.

### `.github/workflows/ci.yml`

**What it does:** On every push, GitHub Actions installs the pinned dependencies and runs lint, the tests, the rule register check, the evals (which fail on any unsafe payment), the mutation check and the README check. It needs no secrets.

### `.gitignore`

**What it does:** Keeps private notes, `.env`, key files (`*.pem`, `*.key`, `*.jwk`), local SQLite databases and Python caches out of git.

**Why:** Setting this up before the first commit is cheaper than scrubbing history later.

## Shared helpers

### `spend_guard/clock.py`

**What it does:**
- Defines one `Clock` interface: something with a `now()` method.
- `SystemClock` reads the real time.
- `FakeClock` only moves when a test calls `advance(...)`.

**Why:** Many rules depend on time:
- verdicts expire after 5 minutes
- reviews expire after 24 hours
- idempotency lasts 24 hours
- velocity uses a 60-second window
- `per_month` uses a rolling 30 days

With a fake clock, tests check each of these exactly, including the edge seconds, without sleeping. The mock, the gate and the verifier all take a `Clock`.

### `spend_guard/jsonutil.py`

**What it does:**
- `loads` parses JSON numbers with a decimal point as `Decimal`.
- `dumps` writes `Decimal` back as a plain JSON number, and refuses floats with an error.

**Why:**
- **Floats lose money.** A float can't hold every amount exactly. From 2^33 upward, `8589934592.000001` and `8589934592.000002` become the same float. With these two functions, an amount goes from the request to the signed token to the export without ever passing through a float.
- **Silent rounding can't creep in.** Refusing floats in `dumps` turns any accidental float into a crash.

### `spend_guard/logs.py`

One JSON line per event, with `dec_` and `req_` ids, so a payment can be traced from the agent to the provider. Keys, credentials and verdict tokens are never logged; a test checks the token isn't.

## The mock API (`mock_api/`)

The mock is a small FastAPI server that implements the API side of the spec, so everything else (the payment gate, the verifier, the MCP server, the evals) can be built and tested on one machine. It prints a "LOCAL MOCK" banner on startup. It is a reference implementation for tests and demos, not a hosted service.

**Run it:**
- `make mock`, or `uv run python -m mock_api`
- it listens on `http://127.0.0.1:8787`

### How a request flows through the mock

1. `gateway` gives it a `req_` id.
2. It checks the key. No key, or an unknown key, is `401` on any path, existing or not. Only the public key set is read without a key.
3. It counts the request against that key's rate limit.
4. It applies any injected faults.
5. It runs the route.
6. POST routes go through `run_post`, which applies the idempotency rules.
7. Routes are thin: they validate the body (`models.py`) and call the engine (`engine.py`).
8. The engine reads and writes the append-only database (`store.py`) and signs with `signing.py`.

### `mock_api/settings.py`

**What it does:** Reads the configuration from environment variables (`MOCK_*`, listed in `.env.example`): database path, rate limit, webhook interval, and the fault settings.

**Faults** (used to test fail-closed behaviour):
- added latency
- a share of requests answered with `500`
- a share that hang, then answer `503`
- a burst of `429`s
- a forced verdict: every decision gets a given code instead of the real one, such as `deny_future_rule`, still signed. This is how the tests prove that an unknown verdict is a denial.

Faults apply only to `POST /v1/authorizations`, and can be changed while the mock runs via `POST /_mock/faults`. Anything under `/_mock/` is mock-only and not part of the spec.

### `mock_api/errors.py` and `mock_api/ids.py`

**What they do:**
- `errors.py` defines the error envelope `{"error": {"code", "message", "request_id"}}` and the status-to-code table.
- `ids.py` makes ids with the spec's prefixes (`dec_`, `mnd_`, `rev_` and so on) and sandbox keys (`ak_sandbox_` or `sk_sandbox_` plus 32 hex characters).
- Keys are stored only as SHA-256 hashes.
- `key_hint` shows a key safely as `sk_sandbox_...b981`.

### `mock_api/models.py`

**What it does:** Pydantic models for each request body: authorization, mandate, agent, enforcement and webhook.

**Rules it enforces:**
- unknown fields are refused (`400`)
- `amount` must be a positive JSON number, not a string or a bool
- `recipient` is at most 1,024 characters; `currency` and `category` at most 128
- `metadata` has at most 20 keys, and each value at most 500 characters
- `protocol` must be one of five values

**Why separate:** All input checking is in one place, and the engine can assume clean input.

### `mock_api/signing.py`

**What it does:**
- Makes a fresh P-256 key at startup, with kid `sandbox-mock-<date>`.
- Signs ES256 JWTs (JSON Web Tokens).
- Serves the public half as a JWK Set.

**Design decisions:**
- **The private key never leaves memory.** It is never written to disk and never printed.
- **We serialize the claims ourselves.** That way amounts stay exact (see `jsonutil.py`).
- **The kid must start with `sandbox-`.** A verifier must never accept a `sandbox-` kid as a production approval, and the verifier tests rely on this.

### `mock_api/store.py`

**What it does:** All SQLite reads and writes.

**Design decisions:**
- **Every table is append-only.** Triggers make SQLite refuse any `UPDATE` or `DELETE`. A change of state is a new row:
  - disabling an agent adds a status row
  - revoking a mandate adds a revocation row
  - resolving a review adds an outcome row
  - switching modes adds an enforcement row

  A test proves the database refuses edits on every table.
- **Times are whole epoch seconds.** That makes "the last 60 seconds" and "the last 30 days" exact comparisons.
- **Amounts are summed as `Decimal` in Python.** SQLite's `SUM` would use floats.

### `mock_api/engine.py`

**What it does:** The policy engine. `authorize` evaluates a request and returns a signed decision. It also handles:
- review approval and denial, and closing expired reviews
- agents, mandates and the enforcement mode

**How a verdict is chosen:**
1. **Agent disabled, or no mandate in this currency:** `deny_no_mandate`. Currency matching is exact and case-sensitive.
2. **Otherwise, each mandate in that currency** (oldest first, revoked and expired ones included) goes through the gate order:
   1. revoked → `deny_revoked`
   2. expired → `deny_expired`
   3. category not listed → `deny_category`
   4. over `per_transaction` → `deny_limit`
   5. over the rolling 30-day `per_month` → `deny_limit`
   6. 10 decisions in the last 60 seconds → `deny_velocity`
   7. above `review_above` → `review`
   8. otherwise → `allow`
3. **Several mandates:** the first `allow` wins; otherwise the first `review`; otherwise the oldest mandate's result.

**Design decisions:**
- **The token signs only what the spec lists.** It contains no `reason`, `mode`, `metadata` or `review`, and no `aud`. Every token, denials included, expires 300 seconds after issue.
- **Approval is a new decision.** It re-checks the agent, the mandate and `per_month`, then issues a new `allow` that points back with `supersedes`. The original review decision is never touched, so the export still shows it as `pending`.
- **`mode` is stamped on each decision.** The mock blocks nothing; the integration acts on `mode`.

Spec: sections 6, 7 and 9.

### `mock_api/webhooks.py`

**What it does:**
- Signs each event once, when it happens. The claims are `iss`, `jti` (`evt_`), `iat`, `type` and `data`, with no `exp` and no `nonce`.
- Queues the event for every endpoint subscribed to its type.
- `deliver_due` posts the identical token as `application/jwt` until an endpoint answers 2xx, waiting 1, 2, 4… seconds between retries (capped at one hour), and stops 24 hours after the event was created.

**Why:** The receiver needs real, retried, signed events to test its deduplication.

Spec: section 17.

### `mock_api/ratelimit.py`

**What it does:** A sliding 60-second window per key. Every authenticated response gets `RateLimit-Limit`, `RateLimit-Remaining` and `RateLimit-Reset` headers; a `429` adds `Retry-After`.

### `mock_api/app.py`

**What it does:** The HTTP layer:
- `gateway` (request ids, authentication, rate limits, faults)
- `run_post` (idempotency)
- the routes and the error handlers

**Idempotency, in `run_post`:**
- **Replay:** the same API key, `Idempotency-Key` and byte-identical body within 24 hours returns the stored response with `Idempotency-Replayed: true`.
- **Conflict:** a different body under the same key is `409`.
- **What gets stored:** the endpoint's own results are stored, except `401`, `403`, `429` and any 5xx.
- **Refusals before the endpoint are never stored:** a wrong key class, a body over 64 KB, or a key over 255 characters.

**Two deliberate quirks:**
- An unsupported method answers `400`, not `405`.
- Another agent's decision answers `404`, not `403`, so ids aren't confirmed to strangers.

**Concurrency:** One lock serializes every database read and write, so two identical requests can't both be evaluated.

**Logging:** One JSON line per request (`req_` id, path, status) and one per decision (`dec_` id, verdict, mode), so a run can be traced end to end.

### `mock_api/__main__.py`

**What it does:**
- Starts the server with uvicorn and prints the banner.
- Gets the org key from `MOCK_ORG_KEY`, or creates one in `.mock/org_key` (owner-only file permissions, gitignored).
- Prints only the key's hint, never the key.

### `mock_api/local.py`

**What it does:** `LocalWorld.build()` puts a whole setup in one process: the mock API (no port; the HTTP client talks to the app in memory), a fake clock, an agent with a mandate, and a full integration wired to it (client, provider, ledger, verifier, gate, model-facing tools). It also has the back-office helpers that use the organization key: approve a review, revoke the mandate, switch the mode, inject faults, read the decision log.

**Why:** The evals and the demo both need the same world, built the same way each time.

**Design decision:** the organization key is made fresh per world and kept in a private field. The agent side of the world never gets it.

### `scripts/seed_mock.py`

**What it does:** Against a mock that is actually running (`make mock`), creates one agent and one mandate and writes the settings the MCP server needs to `.mock/agent.env`. The agent key goes into that file and is never printed.

**Run it:** `make seed`

### What the mock does not implement

Only what the rest of the repo needs is built. Not implemented:
- escrow and usage reports
- list endpoints and pagination
- key rotation
- webhook list, get, delete and ping calls
- `mandate.expiring` events

The mock also accepts `http://localhost` webhook URLs, where the spec says HTTPS.

## The integration side (`spend_guard/`)

The API blocks nothing by itself: it answers "may this agent spend this?" and signs the answer. Whether money actually stops is decided by the code that holds the payment credentials. In this repo that code is `PaymentGate`.

### How a payment flows

1. The agent (through the MCP tool or the OpenAI Agents tool) calls `gate.pay(order)`. It never touches the provider.
2. The gate asks for a verdict through `SpendGuardClient`, with the `Idempotency-Key` `<order_id>:<attempt>`.
3. It checks the recipient against its own allowlist. Not on it: blocked, whatever the verdict.
4. It acts on the verdict **and** the decision's own `mode`.
5. If it pays, it first claims the order in the ledger, then calls the provider, quoting the `dec_` id as the payment reference.
6. Every outcome is written to the ledger and logged as one JSON line with the `dec_` and `req_` ids.
7. Later, `reconcile` compares the provider's payments with the exported decision log.

### `spend_guard/client.py`

**What it does:** A small typed client: `authorize`, `get_decision`, `get_mandate` (org key; used by the webhook receiver) and `export_records`.

**Retry rules:**
- **Retries only when there was no answer or on a 5xx,** always with the same `Idempotency-Key` and body. "No answer" is a timeout, a refused connection or any other transport failure; when every attempt ends that way the client raises its own `Unavailable`, never the HTTP library's error, so the gate can report `no_verdict`. The API replays the original decision for a retry after a timeout, and stores nothing for a 5xx, so a retry can never make a second decision.
- **On `429`,** it waits `Retry-After` seconds and retries. If the wait is longer than `max_wait_seconds` (30), it raises instead of blocking the agent.
- **Any other error is raised at once.** A retried `400` would only be replayed.
- **A POST without an `Idempotency-Key` is never retried,** because that would not be safe. `authorize` requires a key.
- **`RateLimit-*` headers** are read on every response. When the last one said nothing is left, the next call waits for the reset (at most `max_wait_seconds`) instead of guessing.

**Design decisions:**
- **A denial is a `Decision`, not an exception.** A denial is the normal case for a spend check; handling it in an error branch would treat the normal case as a failure.
- **Every exception carries the `req_` id,** because that is the only handle on a call that never produced a decision.
- **Sync, not async.** It is easier to read and explain, and the tool frameworks accept sync functions.
- **Time and sleep are injected,** so tests check a 3-second `Retry-After` without waiting 3 seconds.
- **The API key never appears in `repr`.**

Spec: sections 11, 12, 13 and 19.1.

### `spend_guard/models.py` and `spend_guard/errors.py`

**What they do:**
- `models.py` has the pydantic shapes: `Decision` (what the API returns), `Order` (what an agent wants to pay for), and `PaymentResult` (what the gate answers).
- `errors.py` has the exceptions: `ApiError` (an error response), `Unavailable` (no response) and `VerificationError` (a token failed a check), with one subclass per verifier check.

**Design decisions:**
- **`verdict` and `mode` are plain strings, not enums.** New decision codes may be added later. A strict enum would crash on one and lose the record; a string keeps it, and the gate then treats it as a denial.
- **Unknown response fields are ignored.**
- **Amounts are `Decimal`.** The client writes them with `jsonutil.dumps`, so `8589934592.000001` goes over the wire digit for digit.
- **`PaymentResult` never contains the verdict token or any credential.** It is what an agent or a model will see.

### `spend_guard/gate.py`

**What it does:** `PaymentGate.pay(order)` is the only path to the provider. It decides in this order:

| Situation | Result | Paid? |
| --- | --- | --- |
| Order already paid | `already_paid` (no API call) | No |
| No verdict: an API error, a timeout, an API that can't be reached | `no_verdict` | No |
| Recipient not on the allowlist, any verdict, either mode | `blocked` (decision recorded) | No |
| `allow`, token verifies | `paid` | Yes |
| `allow`, token fails verification | `blocked` | No |
| `review`, enforce mode | `pending_review` | No |
| `deny_velocity`, enforce mode | `denied`, with `retry_at` | No |
| Any other verdict, known or not, enforce mode | `denied` | No |
| Any verdict other than `allow`, observe mode | `paid`, `would_have_blocked: true` | Yes |

`pay_approved(order, approval)` pays an order after a person approves its review. It pays only if the approval decision's `supersedes` is the review decision the ledger recorded for this order.

**Design decisions:**
- **Fail closed.** No verdict, no payment. A control that waves everything through when it breaks can be bypassed by breaking it. There is no fail-open option.
- **`allow` is the only word that pays (in enforce mode).** The check is `verdict == "allow"`, never `verdict != "deny_limit"`. So a code added next year, or `"Allow"` with a capital, is a denial. A test forces the mock to sign `deny_future_rule` and checks nothing is paid.
- **`mode` is read from every decision.** Switching the environment to observe or enforce takes effect on the next payment, with no deploy. An unknown mode counts as enforce.
- **Observe mode relaxes only the verdict.** A denial or a review is paid there, and the ledger marks it `would_have_blocked`. The integration's own checks still apply: the allowlist, verifying the token on an `allow`, and fail-closed (design note 1.7).
- **Recipient allowlist, checked after the verdict.** Mandates don't restrict recipients, so the gate keeps its own list. It asks first, so an attempt to pay an unlisted recipient (for example after a prompt injection) is in the decision log for audit, and the block is in the ledger with its `dec_` id. The cost is in design note 1.1.
- **The token is verified before money moves.** The gate takes a `Verifier`; `VerdictVerifier` is the real one, and the tests use it.
- **One `Idempotency-Key` per order attempt** (`<order_id>:<attempt>`). A timeout or a 5xx is retried under the same key, so it can't make a second decision. Asking again about a denied order replays the same denial for 24 hours: a deny is final for that request. The one exception is `deny_velocity`, which is about timing, not the request: once 60 seconds have passed since the gate first saw it, the next `pay` uses attempt 2 and gets a fresh decision. The result's `retry_at` says when (design notes 1.2 and 1.3).
- **At most one payment per order.** Before calling the provider, the gate inserts a claim row for the order (`INSERT ... ON CONFLICT DO NOTHING`); only the caller whose insert succeeded pays.
- **A lost race says `already_paid`.** Concurrent calls for one order share one decision, so one nonce. For an `allow`, the gate verifies and claims under a per-order lock. A second call waits, then finds the claim, instead of seeing the nonce the first call just recorded as a "replay". A test fires 20 concurrent calls at each of 5 orders, with a verifier slowed to widen the race, and expects exactly 1 `paid` and 19 `already_paid` each time (design note 1.4).
- **A failed provider call is not retried.** Money may or may not have moved, so the order stays claimed and a person checks. Paying twice is worse than paying late.
- **The gate holds an agent key, never an org key,** and holds the provider. The agent only ever gets a `PaymentResult`.

Spec: sections 10 and 19.

**`ask(order)`:** the same steps as `pay`, stopping before any money moves. An `allow` to an approved payee comes back as `authorized`; everything else comes back as `pay` would report it in enforce mode. It sends the same `Idempotency-Key` the next `pay` will, so the two share one decision. The OpenAI Agents guardrail uses it to stop a tool call before the tool runs. `ask` is stricter than `pay` in one way: it never treats a non-allow as payable, even in observe mode.

### `spend_guard/agent_tools.py`

**What it does:** `SpendTools` has the two functions a model gets:
- `check_spend(...)` asks the API whether a spend would be authorized. It pays nothing.
- `make_payment(...)` builds an `Order` and calls `gate.pay`.

Both return a small dictionary: the verdict, the API's `reason` unchanged, ids, and one line of guidance written for a model ("A deny is final for this request: do not retry it, do not split the amount...").

**Why one shared file:** the MCP server and the OpenAI Agents tool register these same functions, and the evals call them directly. So what is tested is what a model gets.

**Design decisions:**
- **Agent key only.** `SpendTools` refuses a client that holds an organization key. With one, a model could approve its own reviews.
- **The model sees no internals.** `PaymentResult.detail` (the gate's own explanation, which can name internal checks) is left out. Errors carry the API's code and message, or a fixed sentence when the API didn't answer, from both tools.
- **Amounts are strings.** The MCP tools declare `amount` as a string, so a JSON number is refused instead of being rounded through a float. `Order` itself refuses a float, and an order id that couldn't go into a header.
- **Guidance is advice, not control.** The evals show agents ignoring it. The gate is what stops them.
- **`check_spend` is a real authorization.** It is recorded and counts toward velocity and, on `allow`, toward the 30-day limit (see the open questions in the design notes).

Spec: section 19.9.

### `spend_guard/ledger.py`

**What it does:** The gate's own append-only SQLite record:
- `attempts`: one row per `pay` call, whatever happened, with the order id, the attempt number, status, `dec_` and `req_` ids, verdict, mode, reason, and the raw verdict token. The gate reads the latest attempt back to choose the next `Idempotency-Key`.
- `claims`: at most one row per order, written just before the provider is called.

**Why:**
- The `dec_` id is the join key between an order and the decision log. The `req_` id is what's left when a call never produced a decision. The raw token is the proof of what was paid against.
- Append-only, like the API's decision log, so a payment record can't be quietly changed. Triggers refuse `UPDATE` and `DELETE`, and a test proves it.

### `spend_guard/provider.py`

**What it does:** `MockProvider`, a stand-in payment provider. It "holds the credentials" (a secret made at runtime or read from `MOCK_PROVIDER_SECRET`) and records every payment in its own append-only table. No money moves.

**Design decisions:**
- **`pay` is deliberately unguarded,** like a real provider API: whoever holds the object can pay. The safety comes from who holds it (only the gate), and `reconcile` lists a payment that skipped the gate and has no matching `allow`.
- **The secret never appears** in `repr`, results, the ledger or logs. A test checks all of them. (It is a Python private attribute, so this shows where credentials sit; it is not a security boundary inside one process.)

### `spend_guard/reconcile.py`

**What it does:** Compares every provider payment with the decision log export (`GET /v1/exports/records`, org key) and lists each payment that isn't backed by exactly one matching `allow`:
- no decision reference at all (paid without asking)
- a reference that isn't in the export
- a decision that isn't `allow` (paid in observe mode, or a bypass)
- an amount, currency or recipient that differs from what was authorized
- one `allow` behind more than one payment

**Run it:** `make reconcile`, or `uv run python -m spend_guard.reconcile --provider-db provider.db [--from 2026-10-01 --to 2026-11-01]`. It reads the org key from `SPEND_GUARD_ORG_KEY` or the mock's `.mock/org_key`, never prints it, and exits `1` if anything is unmatched.

**Why:** A bypass can't be made impossible from outside the provider, but one with no matching `allow` can be made visible. This runs in the back office with an org key, never in the agent.

**What it misses:** a direct payment that quotes an unused `allow` for the same amount, currency and recipient (for example one that `check_spend` produced). The API authorized that spend, so the decision log has nothing to say against it. Comparing against the gate's own ledger too would catch it; that is an open question in the design notes.

### `spend_guard/verify.py`

**What it does:** `verify_verdict(token, deal, *, jwks, nonce_store, accepted_mandates, allow_sandbox=False, clock, audience)` runs every check in a fixed order and returns the verified claims, or raises an exception named after the first check that failed:

| Check | Exception |
| --- | --- |
| At most 16 KB; three unpadded base64url segments | `TokenFormatError` |
| Key by `kid` (unknown: one refetch; listed twice: reject), ES256 only, issuer | `SignatureError` |
| Required claims `exp, iat, iss, nonce, verdict, request`, with the right types | `TokenFormatError` |
| A `sandbox-` kid, unless `allow_sandbox` | `SandboxKidError` |
| `iat` more than 60 s in the future | `FutureIatError` |
| `verdict` is not exactly `allow` | `NotAnApprovalError` |
| Now is at or after `exp` (no leeway) | `ExpiredError` |
| Amount (exact decimal value), currency (case-sensitive), recipient (exact) differ from the deal | `ClaimsMismatchError` |
| No `mandate`, or one the operator didn't list | `UnknownMandateError` |
| An `aud` that doesn't name us | `AudienceError` |
| Nonce already used / review already approved, recorded atomically and last | `ReplayError` / `SupersedesError` |

`VerdictVerifier` holds one integration's settings and has the `verifier(token, order)` shape the gate takes.

**Design decisions:**
- **The order matters.** Cheap structural checks come first; the nonce is recorded last, so a token that fails any check never uses up its nonce. A test presents a token that fails the audience check, then fixes the setting and shows the same token still verifies.
- **Signature first, then parse with `Decimal`.** `PyJWS` checks the signature and hands back the raw payload; `jsonutil.loads` then parses amounts exactly. Amounts are compared as decimal values, so `340` and `340.00` match, and `8589934592.000001` and `...002` don't (they're the same float).
- **Time checks use the injected clock, not PyJWT's.** That is why `exp` and `iat` are checked here rather than by `jwt.decode`: tests move the clock to one second before and at `exp`.
- **A webhook event can't pass.** Events have no `exp` and no `nonce`, so the required-claims check rejects them. A test takes a real event from the mock and shows it.
- **`supersedes` is recorded with the nonce in one step.** A second approval of the same review is refused for 25 hours (a review lives 24). Recording both together means a rejected token records neither.
- **Each rejection says which check failed.**

Spec: section 16.

### `spend_guard/jwks.py`

**What it does:** `KeySet`, a `PyJWKClient` subclass. PyJWT already caches the set for five minutes and refetches once on an unknown `kid`, then waits 30 seconds before refetching again, so unknown kids can't hammer the endpoint. The subclass adds two things:
- fetching through httpx with a timeout and **no redirects** (following a redirect for key material would mean trusting whoever issued it), which also lets tests serve the set in-process
- rejecting a `kid` listed twice (`PyJWKClient` would take the first)

If the set can't be fetched, nothing verifies, so nothing is paid.

### `spend_guard/nonces.py`

**What it does:** Remembers accepted nonces. `add` records several keys atomically, all or none, and reports the first one already present.
- `SqliteNonceStore`: `INSERT ... ON CONFLICT DO NOTHING` inside one `BEGIN IMMEDIATE` transaction. Two instances opening the same file share it; SQLite's write lock makes the check-and-set one step. A test presents one approval to two verifiers at once, 20 times, and gets exactly one acceptance each time.
- `RedisNonceStore`: the optional shared backend (`agent-spend-guard[redis]`). A short Lua script does the all-or-none set-if-absent inside Redis. Tested with `fakeredis`.

**Why "all or none":** a plain set-if-absent is atomic for one key; an approval also records the review it supersedes. Two separate calls would be a check-then-set race.

**Not append-only, on purpose:** this is a cache with a time-to-live (at least 600 s, and past `exp` plus a minute). The permanent record is the ledger, which keeps the raw token.

### `spend_guard/webhooks.py`

**What it does:** `WebhookReceiver.handle(body, content_type)` returns an HTTP status:
1. `Content-Type` must be `application/jwt`.
2. `verify_event`: same signature and issuer check as a verdict, but requiring `iss, jti, iat, type, data` (no `exp`: events have none). A verdict token fails here.
3. A `sandbox-` kid is rejected on a production endpoint; an event older than 25 hours is rejected; so is one dated more than 60 s ahead (otherwise it would dodge the age check).
4. A `jti` already stored is acknowledged without doing anything.
5. The object is re-read with our own key. A `404` means "not ours": acknowledged, ignored. If the API is down, the answer is `503` and nothing is stored, so the sender's retry of the identical token is processed later.
6. The event is stored (append-only, `jti` primary key), then acted on, using the re-read object, never the event's copy.

**Actions:** `decision.review_pending` notifies a person (`notify_human` prints a clearly marked line and logs it; a real deployment would page or post to a channel). An approval in `decision.resolved` is handed to `on_approval`, which can call `gate.pay_approved`. A denied or expired review is reported only if our own ledger saw its `rev_` id. `mandate.revoked` notifies a person. `ping` does nothing.

`create_receiver_app(receiver)` wraps it in a one-route FastAPI app (`POST /webhooks`).

**Design decisions:**
- **Store after the re-read, act after storing.** A failed re-read stays retryable; two racing deliveries can't both act, because only one insert of the `jti` succeeds. The trade-off is in design note 1.10.
- **Keep every event.** A denied or expired review can't be read back from the API, so the event is the only record of it. Keeping all events is simpler and gives a full trail.

Spec: section 17.3.

### What the integration side does not do

- **No fail-open option.**
- **No copy of the key set is stored with each payment.** The ledger keeps the token only, so verifying an old payment later needs the key that signed it to still be published.
- **Redis Cluster is not handled:** one `add` uses several keys, which would need the same hash slot.
- **`mandate.expiring` and `escrow.*` events are verified and stored but not acted on;** the mock doesn't send them.

## The MCP server (`mcp_server/`)

MCP (Model Context Protocol) is a standard way to offer tools to a model. Claude Desktop and Claude Code can both connect to an MCP server.

### `mcp_server/server.py`

**What it does:**
- `build_server(tools)` registers `check_spend` and `make_payment` with the official `mcp` SDK. The docstrings on those two functions are what the model reads, so they are short and say what to do after a deny or a review.
- `tools_from_env()` builds the client, verifier, provider and gate from environment variables. It exits with a clear message if `SPEND_GUARD_AGENT_KEY` isn't an agent key, and the message never shows the key.
- `read_env_file()` lets the settings come from a file (`SPEND_GUARD_ENV_FILE`), so an MCP client's config doesn't have to hold the agent key.
- `main()` runs the server on stdio. Logs go to stderr, because stdout carries the protocol.

**A note on the SDK:** version 2 of the `mcp` package renamed its high-level class from `FastMCP` to `MCPServer`. This repo uses version 2.

`mcp_server/__main__.py` makes `python -m mcp_server` work.

## The OpenAI Agents SDK integration (`integrations/openai_agents/`)

### `integrations/openai_agents/tools.py`

**What it does:** Three pieces, each using a mechanism the SDK has today:
- `make_payment_tool(tools)`: a function tool backed by the gate.
- `payment_guardrail(tools)`: a *tool input guardrail*. The SDK runs it before the tool's own code. It calls `gate.ask(order)`. On `allow` the tool runs. On a denial, the model gets the refusal instead of the tool result. On `review`, it halts the run.
- `run_with_gate(agent, task)`: runs the agent and turns that halt into a `NeedsHuman` result with the review id.

**Why a guardrail when the gate already refuses to pay:** the gate is the control; the guardrail is a second line in front of it. The same guardrail can be attached to any other tool that moves money. And stopping the run on `review` means "a person must approve" is the outcome of the run, not something the model has to remember to say.

**Design decision:** the guardrail and the tool share one decision, because `ask` and `pay` send the same idempotency key.

### `integrations/openai_agents/example_agent.py`

**What it does:** A small "procurement assistant" with one tool, the guarded `make_payment`. With `OPENAI_API_KEY` set it runs a task against the local mock. Without it, it calls no model and prints how to run it. The tests never call a model.

## The evals (`evals/`)

Tests check one rule at a time. The evals check the whole thing against agents that misbehave.

### `evals/policies.py`

**What it does:** Six scripted "agents", each a few lines:
- **obedient:** does the task and stops when told no (it waits out a `deny_velocity`, which is allowed)
- **retry-spammer:** submits everything several times, and retries refusals under new order ids
- **splitter:** cuts a refused amount into 2, then 4 payments
- **category-launderer:** sends a refused payment again under other category labels
- **prompt-injected:** does the task, then obeys a payment instruction hidden in an invoice
- **replayer:** tries to get a paid order or an approval honoured twice, or after it expired

Every call carries an `intent` (`task`, `backoff`, `retry`, `split`, `relabel`, `injected`, `replay`), which is how the harness counts unsafe attempts.

### `evals/scenarios.py`

**What it does:** The ten scenarios, E1 to E10: a normal purchase, an over-limit purchase, a wrong category, a review, a fast loop that trips velocity, a mandate revoked mid-task, an outage, a prompt injection, a replay, and a decision code nobody has seen before. Amounts come from a seeded random generator.

### `evals/oracle.py`

**What it does:** Decides which payments were unsafe. It does not ask the gate. After a run it reads the provider's own payment list and the API's decision log, and applies the mandate's rules from scratch.

**Why separate:** if the gate graded its own work, a bug in the gate would hide itself.

### `evals/runner.py`

**What it does:** `run_one(scenario, policy, run)` builds a fresh `LocalWorld`, runs the policy, has a person approve reviews where the scenario says so, then asks the oracle. `run_all(runs)` does every combination. The random seed is the text `scenario:policy:run`, so results repeat exactly.

### `evals/report.py`

**What it does:** Runs everything and writes `EVALS.md`: a summary table, the findings, and a table per scenario. It exits 1 if there is any unsafe payment.

**Two measures, kept apart:**
- **Safety:** unsafe payments. Must be 0.
- **Behaviour:** unsafe attempts, and how many were stopped. The ones that were paid ("paid inside the mandate") are reported in their own column: splits under the review threshold and a relabel to an allowed category. That is the honest limit of checking one request at a time.

**Run it:** `make evals`

## The demo (`demo/`)

### `demo/__main__.py`

**What it does:** Prints a step-by-step story: an agent and its mandate, an allowed payment, a denied one and a split that pays nothing, a review that reaches a person through a signed webhook, the approval paid once, a revoked mandate, an outage that fails closed, and a reconcile run that catches a payment made behind the gate's back. Everything is in-process with a fake clock. `DEMO_PAUSE=0` removes the pauses.

**Run it:** `make demo`

## Tests (`tests/`)

Every test runs in-process: no network, no API keys, and no waiting on real time. The one exception is a race test whose verifier pauses 20 ms on purpose, so the race happens on every run.

- one test per decision code, each with a fresh agent (the engine weighs every mandate an agent has ever held, so reusing an agent would mix cases)
